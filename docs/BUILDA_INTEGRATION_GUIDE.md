## 1 接入前先定清楚权威边界

### 1.1 先选玩法模型

确定客户端引擎、Room 语言、房间类型、人数、进入方式、离开和空房回收方式。公共长驻世界、循环对战房、一次性匹配对局的生命周期不同，不能只复制同一段进房代码。

本项目是七人公共长驻世界，使用 `pasture-world` 作为匹配入口，每人一块牧场；客户端调用 Room 模式的公开加入接口。项目口语中的 Open World 对应这个业务入口，并不是另一个需要凭名字猜测的服务。

### 1.2 把状态分成三类

| 状态 | 本项目归属 | 接入要求 |
| --- | --- | --- |
| 现金、训练成长、蛋血量、孵化归属、携带物、购买结果 | Room 权威状态 | 客户端发意图，Room 校验并结算，再发结果 |
| 玩家位置 | 客户端即时响应，Room 校验后采纳 | 限制速度、位移预算、边界与序号；其他玩家显示服务端采纳的位置 |
| 骨骼动画、粒子、飘字、镜头、界面 | 客户端表现 | 从权威状态驱动，尽量本地播放，不逐帧广播 |



客户端上报位置并由服务端校验，是本项目选择的折中方案，不等于完整的服务端输入模拟。涉及更强对抗、排名或奖励时，应重新评估信任边界。

### 1.3 存档和身份先隔离

- 开发单机档、离线试玩临时档、正式联机档分开；不要自动把开发资源导入正式经济。
- 玩家身份以宿主和连接上下文为准，不接受请求体指定其他玩家的账户。
- 购买、奖励、孵化、订单结算使用稳定操作 ID 和幂等处理，重复回执不能重复发货。
- `privateKV`、Room 云状态及本地存储用途不同。查询到某个存储为空，不代表另一套存档损坏。
- “同机同网另一个号能进入”只是排查线索。先获取必要的玩家 ID、失败阶段和错误码；不要直接清档或认定账号异常。

### 1.4 支付广告和排行榜要完成平台闭环

商品 ID、存档键和排行榜 ID 保持稳定，展示名称可以变化。运行商品表必须与发布 manifest 的 `payPoints` 对齐，排行榜也要有对应声明；只接界面和运行代码，不会自动更新平台配置。

本项目早期单机支付由客户端发货，联机后由 Room 接管。按当前 `grantBy` 走对应结算流程，不能让两端同时发货。发货结果与幂等标记持久化后再完成订单处理，失败、取消和重复回调分别测试；本地模拟成功不等于真实 G 币支付已验收。

早期 KV 存档设计中，批量写不能当成原子事务，采用非活动分块写入、回读校验、最后提交指针。接入 Room 后应遵循 Room 云状态契约，不能把旧客户端保存路径继续当成权威账本。重点测试部分写入失败、响应丢失、刷新和恢复。

广告完成回调、奖励请求和 Room 发奖是不同步骤。取消或失败不奖励，重复请求要幂等；广告窗口关闭后恢复宿主忙碌状态和玩家输入。排行榜显示正常，也不能证明跨账号榜单、提交策略和公开版本配置全部生效。

## 2 分清版本和两条发布链

### 2.1 版本各自解决什么问题

| 标识 | 用途 | 不能用它推断什么 |
| --- | --- | --- |
| CLI 和 Skill 版本 | 本机工具及操作说明 | 不代表游戏已更新，也不等于 SDK 版本 |
| `.builda-agent/sdk-version` | 项目的 SDK 版本锁 | 不能因工具自更新就随意改锁或只换一个 SDK 文件 |
| 客户端草稿版本、Bundle ID | 标识上传的客户端内容 | 不等于线上公开版本，也不是 Room 协议兼容键 |
| `onlineCompatibilityRevision` | 客户端与 Room 的游戏协议兼容分组 | 不是打包次数、代码哈希或账号修订号 |
| Room Artifact、Server Release | 不可变服务端产物及激活版本 | 激活新版不会把正在运行的旧房间热换成新版 |



SDK 自身的传输协议版本、移动包首字节的帧格式版本、`onlineCompatibilityRevision`、账户操作 revision 也不是同一个概念。本次兼容修订为 2，移动帧版本仍为 1。

### 2.2 客户端和服务端分别发布

```text
客户端源码 → 构建目录 → Bundle ZIP → Builda 待发布草稿 → App 内审核和公开发布
Room 源码 → 平台构建 → 不可变 Artifact → 激活 Server Release → 新 Ticket 和 Room
```

`builda publish` 完成的是客户端上传和草稿同步。成功回执中的“当前版本”不能直接写成“所有线上玩家已更新”。公开发布仍按 App 流程完成。

只修复兼容的服务端逻辑，现有客户端可以继续使用；本次移动数据容器修复就是这种情况。若修复的是客户端代码，部署 Room 无法替代更新客户端包。

### 2.3 什么时候改兼容修订

每次修改先回答：旧请求还能接受吗？旧客户端能理解新响应吗？进房、重连、退出流程还成立吗？三项均成立时，通常保持修订号。

真正破坏兼容时，按当前工具约定完成：**同步新修订客户端草稿 → 部署并激活同修订 Room → 用户在 App 发布客户端 → 玩家更新并重新进入。** 本项目曾按用户明确要求从 1 升到 2，那次版本隔离本身不构成故障修复证据。

已有 Ticket、Assignment、Room 保留创建时固定的版本。不能靠修改配置、修改本地 Bundle ID，或把 `migrate-room` 当成升级代码的命令，让旧对象热切换。部署后双方重新进入，并通过日志核对实际 Artifact；不能只看“已经重进了”。

## 3 建立可复现的本地环境

### 3.1 使用项目工具链和同一份 Room 源码

在本项目 `h5-map/` 目录执行命令。先检查 `.builda-agent/SKILL.md`、锁定 SDK 指南和 `.agents/skills/builda-online/SKILL.md`，使用项目内的官方启动器。

```powershell
.\.builda-agent\builda.cmd check
.\.builda-agent\builda.cmd sdk check
.\.builda-online\bin\builda-online.cmd check --room-source server/game
```

检查应确认 SDK 与 Online 发行快照一致，Room 源码恢复检查通过。需要升级时按官方整套升级流程处理，不手工替换 SDK 文件，不绕过恢复或源码路径检查。

克隆包含大资源的仓库后确认 Git LFS 内容已拉取。缺少真实模型、只剩 LFS 指针文件，会把资源问题伪装成加载或渲染问题。

Windows 上注意带空格路径和 `.cmd` 包装器的参数引用。本项目曾遇到部署工具子进程路径转义问题；这是工具启动层故障，不应通过改协议、改游戏 ID 或绕过授权处理。凭据由官方授权流程保管，不要求用户在聊天中粘贴密码或令牌。

### 3.2 两个服务是不同职责

本项目本地联机需要：

| 服务 | 端口示例 | 职责 |
| --- | --- | --- |
| 官方 Room Mock | 7350 | 执行 Room 源码、接收消息、维护本地权威状态 |
| Builda 测试外壳 | 18090 | 提供宿主 SDK 模拟和 H5 客户端页面 |

启动 Mock 的项目命令：

```powershell
node server/mock/typescript/src/cli.mjs --room server/game/room.ts --source-root server/game --sdk server/typescript --scenario builda.room.local.json --port 7350
```

另开一个终端启动外壳；`$buildaGameId` 替换为当前项目绑定的真实游戏 ID：

```powershell
$buildaGameId = '填写当前项目的 gameId'
node tools/prepare-builda-draft.mjs --diagnostics
.\.builda-agent\builda.cmd dev --web build/builda-draft --port 18090 --game-id $buildaGameId
```

以工具输出的外壳地址为准，在已有查询参数后分别附加：

```text

&builda_mock_player=player-2&builda_mock_name=Player2
```

这两个身份必须存在于本地 Scenario。重复打开同一身份不能当成双玩家测试，还可能产生重复占用或连接冲突。

### 3.3 避免测错进程和产物

- Room 代码改了，要确认 Mock 已加载新代码；没有热更新证据就重启对应进程。本项目曾因旧 Mock 不认识新礼包操作而卡在广告调用前。
- 外壳通常服务构建目录，修改 `public/` 不等于页面马上更新。检查构建文件，再刷新页面。
- 先核对监听端口、进程和启动目录；不要误杀其他项目的服务。
- 普通 `serve.py` 静态预览不等于 Builda 外壳，更不等于 Room Mock。
- 真实 App 也可能从设备上的 loopback 地址加载 Bundle。只能按官方显式 Mock 标志识别测试环境，不能拿 `localhost` 当开关。
- Mock 内存云档重启会重置，不能据此判断真实玩家存档丢失。

## 4 协议边界要兼容宿主数据表示

### 4.1 本次移动完全不同步的根因

旧解码器先判断：

```js
if (!(bytes instanceof Uint8Array)) throw Error('INVALID_MOVE');
```

这个判断依赖当前 JavaScript 环境的构造器身份。线上实际观测到：帧长 23、版本 1、玩家已加载且活动，但 `instanceof Uint8Array` 为 false；结果全部拒绝。日志没有证明宿主到底传入普通数组还是另一上下文的视图，不应把其中一种猜测写成平台事实。

本地 Mock 使用本环境的 Uint8Array，原有“自己编码、自己解码”测试一直通过。服务端因此始终记录出生点，位置无法广播更新；敲蛋也因权威位置未更新而连带失败。修复后线上确认双方接受移动持续增长，4 次敲蛋全部成功。

### 4.2 修复原则

先验证长度上限，再把非本地字节容器逐项验证为 0..255 的整数并复制到本地 Uint8Array，最后执行原协议解码。原生 Uint8Array 保留快速路径。

必须继续校验帧版本、长度、数值有限性、flags、玩家槽位、序号和业务位移。不要直接 `Uint8Array.from` 后就认定输入有效，因为它会把越界值或非整数转换成其他字节，掩盖非法输入。

本项目单移动帧为 23 字节，七玩家批次最多 174 字节；上限在分配前检查。编码、小端格式和兼容修订均未改变。

实现：[共享协议](../h5-map/public/online/protocol.js)。服务端副本由 `tools/build-online-rules.mjs` 生成，不手改生成文件，不修改 SDK。

### 4.3 本地就能补足的测试

至少覆盖固定的独立字节样本、普通字节列表、另一 JavaScript 上下文的视图、非零 byteOffset、截断/超长、错误版本、空洞、字符串、非整数、越界字节、NaN 坐标、旧序号与环回。

再把这些输入送进真实业务规则，验证移动被采纳、checkpoint 后继续移动、瞬移被拒、移动到蛋旁边后能够扣血。只测编解码往返不够。

专项：[test-online-byte-boundary.mjs](../h5-map/tools/test-online-byte-boundary.mjs)。旧代码 6 项中 5 项失败；修复后 6 项全部通过，已纳入 `npm run test:online`。

## 5 把连接做成完整生命周期

### 5.1 记录阶段并等待完整基线

推荐诊断顺序：配置 → 身份鉴权 → 网关 → 申请进房/Ticket → 房间连接 → 初始基线 → 运行。

本项目 `ready` 需要玩家、账户、蛋、动物四类完整初始基线。分片尚未收齐或断线后沿用旧基线，都不能开始正式操作。重连时清空旧屏障和未完成分片，再建立新基线。

`ready=true` 只证明初始化完成。持续可玩还要看移动是否发送、服务端是否采纳、下行是否收到、远端是否应用以及操作是否有回执。

### 5.2 外层超时不能遮住 SDK 的真实错误

本项目曾给整个连接流程设置 15 秒总截止时间，而锁定 SDK 的单次通道等待就可能到 15 秒，还存在 ICE 收集及有界重试。结果外层总先报 `ONLINE_TIMEOUT`，把实际失败阶段掩盖掉。

排障时为诊断包增加足够的观察窗口，并在清理前保存安全错误码和阶段。本项目诊断包曾改为 180 秒；这是排障配置，不是所有正式游戏都应采用的等待时长。正式超时策略要结合 SDK 流程、取消机制和用户体验单独验收。

### 5.3 超时后的迟到结果也要结算

取消或超时后标记该尝试已放弃，忽略迟到的业务回调；仍按 SDK 契约结算已有 Ticket 和 Room。结果不确定时复用幂等键恢复，不能直接再开一个 Admission。

服务端拒绝、重试耗尽、临时重连、最终关闭要有不同结果。尤其要防止一次操作回执丢失后，整个客户端永远停在待处理状态。

### 5.4 网络失败不要拖垮人物帧

本项目帧循环在人物更新前执行联机更新。装备同步发送若抛异常，会中断后续人物与镜头更新。发送器需要有界退避、只保留最新状态、成功后才记为已同步，并把失败交给连接状态管理。

异常隔离要针对具体发送边界，不能给整个主循环套一个空 catch，把所有错误吞掉。装备发送问题曾在代码检查中发现并修复，但不能把它当成当时真机冻结的已证实根因。

## 6 一次诊断就覆盖完整链路

### 6.1 从症状选择证据

| 现象 | 优先查看 | 不能直接下的结论 |
| --- | --- | --- |
| UI 能点，摇杆不动 | 指针事件、覆盖层、触控归属 | 一定是联机问题 |
| 摇杆动，人物与镜头不动 | ready、主帧计数、暂停和输入锁、异常位置 | 一定是触摸代码坏了 |
| 本人能走，别人眼中不动 | 收到/采纳移动数、权威坐标、下行和应用数 | 看到两个人就说明同步正常 |
| 挥镐有动画，蛋不掉血 | 操作回执、权威位置、代次、距离、冷却和装备 | 动画播放代表服务端命中 |
| 连接失败，没有 Room handle | SDK 阶段、错误码、Ticket 状态 | Room 日志为空代表服务端健康 |
| 突然冻结且 ready=false | roomClosed、关闭码、Room 告警与退出原因 | 没有 JS error 就没有故障 |

### 6.2 第一轮就记录拒绝原因

低频样本应包括以下内容，而不是每个网络包写一条日志：

- 身份和版本：必要的业务玩家 ID、Room ID、Artifact、客户端 Bundle、兼容修订。
- 连接状态：connected、loaded、active、阶段及最近关闭码。
- 移动链路：发送数、服务端收到数、采纳数、最近序号、权威坐标、下行接收/应用数。
- 拒绝分支：解析失败、序号、频率、边界、距离、垂直位移。看增量和发生时间，不能把“最近一次拒绝”当成此后所有包均拒绝。
- 关键操作：收到数、成功数、拒绝原因和超时；只记录必要字段。

本项目现有服务端 `network_sample` 覆盖收到、采纳、活动状态、包元信息和敲蛋结果；完整的客户端发送/接收/应用计数属于后续完善方向，不能假称已全部实现。

第一次只记录“收到多少、接受多少”，确认了全拒绝，却没记录具体分支，导致又部署一轮、让用户重进一次。这是诊断设计不足，应在首轮就补齐。

### 6.3 D3 的作用和边界

D3 显示 ready、阶段、帧计数、更新阶段、hidden/paused/busy/locked/training、触控值、坐标和精简错误信息。它能区分输入、门控、主循环和连接状态，但不能单独证明权威同步成功。

临时面板只在明确的诊断构建启用，正式构建关闭。不得通过强行设 ready、解除所有输入锁或跳过服务器校验，让画面“看起来能动”。

### 6.4 官方日志和告警的读法

先查短窗口；未知 Room ID 时查当前游戏，再按返回的 Room 缩小范围。检查 `has_more`、`partial`、`dropped_events`、`dropped_bytes`。

空结果不证明健康；404 可能是该 Room 没有可查询记录，503 是查询不可用；`exit=null` 也不是存活保证。告警是平台观测，业务日志是游戏代码记录，二者需要按 Room、Artifact、generation 和时间对应。

只记录安全错误码和必要业务字段。不记录 token、完整 Assignment、SDP/ICE、密码、完整玩家输入、完整存档或支付敏感内容。不要用玩家 ID 代替 Room ID 查询。

## 7 服务端性能和可恢复性一起设计

### 7.1 少量守卫也可能产生大量计算

成本取决于搜索空间、重复次数、每个邻居的工作和恢复开销，不只取决于守卫数量。本项目的热点包括多次 A*、不可达目标反复搜索、邻居检查中的矩阵创建/求逆、逐帧对象和数组重建。

真实告警曾出现 `ROOM_FUEL_EXHAUSTED`，单个生命周期回调达到 2,000,000,000 fuel 并终止房间。fuel 是执行指令预算，不能换算成“几毫秒”或“允许几个守卫”。

锁定版本的关键限制如下；完整约束以[资源限制文档](../h5-map/.agents/skills/builda-online/references/resource-limits.md)为准：

| 项目 | 锁定版本限制 | 设计要求 |
| --- | --- | --- |
| 单回调 fuel | 2,000,000,000 | 搜索、递归和循环有全局工作上限 |
| 单 Room WASM 内存 | 64 MiB | 控制实体、任务和缓存数量 |
| 单 checkpoint | 4 MiB | 统计整个世界，而非仅某个子系统 |
| 单回调 Host 命令 | 256 | 合并发送，避免每对象每帧调用 |
| 单完整 CYR1 帧 | 65,535 字节 | 计入头部与消息类型，不能只算 payload |

`ROOM_FUEL_WARNING` 等观察告警与 `ROOM_FUEL_EXHAUSTED` 这种终止事件不同。一定读 `action`、`metric`、`scope`、`window_millis` 和 `limit`，不能一看到 warning 就告诉用户“房间被停了”。

### 7.2 本项目的优化路径

先用全守卫共享搜索预算止住无界工作，再把常态工作移出运行时：

1. 构建时烘焙合法边、连通分量、巡逻树和锚点，巡逻不再运行 A*。
2. 追击先用合法直达、缓存或有效树走廊，必要时增量 A* 优化路径。
3. 每 tick 所有任务合计最多 600 次出堆，过期堆项也计入预算；公平配额后再按追击和等待优先分配。
4. 同一目标移动不反复取消任务；预算不足跨帧续算，已有有效路线继续走。
5. 对搜索节点、堆、路径长度、重试频率和缓存设上限；路径保存格子 ID，避免反复复制三维点。

代价要讲清楚：重规划可能延后，过渡路线未必最短；巡逻锚点改变闲逛路线分布。不能只说“性能变好了，没有任何影响”。具体实现和测试见[守卫导航](GUARD_NAVIGATION.md)。

### 7.3 缓存不能偷偷改变恢复后的行为

会影响未来判定的任务、路线、退避、时钟、随机进度必须进入权威 state，或有确定的恢复办法。不可变地图数据可以共享；只为加速的索引可以重建，但不能藏着一份推进中的游戏状态。

本项目尝试跨帧缓存 eggEngine 时，恢复检查未通过，随后删除该缓存而不是绕过检查。另一处路线消费数组与缓存共享引用，导致消费路线时缓存也变了；使用独立数组后，逐 tick checkpoint 恢复才与连续运行一致。

恢复测试应在寻路、追击、携带、购买等待等过程中插入序列化/恢复，比较后续轨迹与结果。只在空闲状态保存一次不够。

### 7.4 区分三种性能证据

Node 基准用于比较本地算法开销；线上告警用于观察 WASM fuel、执行和流量；真机采样用于证明帧率、发热和内存。本项目同口径单次 Node 导航基准从约 894ms 降到 412ms，不等于线上 fuel 减半，也不等于手机达到 60fps。

## 8 手机输入和宿主生命周期单独验收

### 8.1 桌面鼠标不能替代多指测试

本项目旧手势在第二根手指落下时清空移动，导致不能边走边转镜头。修复后在按下时固定手势归属：左侧移动、右侧镜头、两根右侧手指缩放；跨过中线不重新分配，抬起右手不取消左手移动。

检查 touchcancel、失焦、进入后台和宿主暂停时是否清理 touches、touchMove、按键和攻击计时，防止恢复后卡住或继续移动。UI 开关、广告、支付等忙碌状态结束后也要正确恢复。

### 8.2 先识别被谁挡住

- 旧攻击按钮曾仅被 `pointer:fine` CSS 隐藏，手机仍显示。不要未经包内容核对就归因于缓存。
- 覆盖层、`pointer-events`、层级和禁用按钮会拦截点击；Auto Swing 曾遮住另一弹窗的按钮。
- 账户更新时重建整张商品列表，会在鼠标按下与松开之间移除目标节点，造成 click 丢失。按键、卡片原位更新，并保留滚动和焦点。
- 联机分支提前 return 曾跳过巨蛋倒计时牌的创建。共享表现初始化放在恰当位置；只有权威模拟本身由联机分支替代。
- 训练收益低频同步，不代表飘字只能低频出现。表现按本地节奏播放，余额和成长仍以 Room 结果为准。

### 8.3 版本和画面检查

横屏配置、宿主安全区、viewport 和触控适配一起检查。记录实际 Android WebView/Chrome 内核；手机系统版本、桌面 Chrome 版本和 manifest 的最低内核声明都不能替代实测。

本项目构建声明最低 Chrome 93，但一次在更新内核上的成功不能证明最低版本已覆盖。`dvh`、`cqw` 等 CSS 特性需要按目标版本提供回退或验收。

设备允许时用 USB 调试读取画面及相关日志。App 没有暴露 WebView 调试入口时，不假称能读取页面内部状态；使用显式诊断构建补充必要证据。一个截图显示界面正常，也不能代替持续移动、前后台切换和多指操作验证。

## 9 打包与发布要有明确产物边界

### 9.1 从运行目录打包

客户端包只包含运行必需资源。排除源代码、Room 源码、测试页、原始导出、缓存、凭据、日志和构建中间件；Room 则部署完整的受检源码根目录及依赖。

本项目曾以单文件入口部署时被路径检查拒绝，改为完整 `server/game` 目录后通过。解决源码边界，而不是把依赖搬到未检查的位置或绕过限制。

工作区有其他尚未发布功能时，先明确本次发布包含哪些改动。只改客户端两个文件的热修复可从已确认的发布包制作最小补丁；Room 仍应维护一份可检查、可测试的真实源码。不要把打包动作当成默认发布整个工作区。

### 9.2 草稿开关必须检查产物

本项目构建脚本：

| 模式 | 命令 | 产物行为 |
| --- | --- | --- |
| 普通草稿 | `node tools/prepare-builda-draft.mjs` | 可有隔离的离线试玩，默认无诊断面板 |
| 诊断草稿 | 同命令加 `--diagnostics` | 启用临时诊断 |
| 正式客户端 | 同命令加 `--release` | 关闭诊断和草稿离线试玩 |

三种模式均输出到本项目 `build/builda-draft`，会重新生成该目录；构建后核对实际 `draft-preview-config.json`。目录名叫 draft 不决定最终模式，App 也不会自动剥离诊断代码。

本次 D3 暂时保留用于验证。将诊断包提交公开发布前，应重建正式产物并检查，不能只在口头上说“正式版本”。

### 9.3 离线试玩必须隔离

失败后的离线试玩使用临时内存账户，不读写正式云档、不参加排名、不执行正式支付和奖励结算。恢复联网不能把临时资源迁入正式账户。

运行中的正式 Room 终止，应给出重连或退出路径；不能为了让人物继续动，把当前权威账户静默切成单机状态。

### 9.4 大包和回执

本项目客户端约 130MB，主要为模型、贴图、音频。体积提示需要评估，但排查联机故障时不宜同时大改资源拆包，破坏复现条件。拆包和按需加载应有资源可用性、缓存及弱网验收。

等待命令最终退出成功，再读取本次回执，核对 Bundle、Artifact 和源码哈希。部署进程尚未结束时读取 `last-deployment.json`，可能拿到上一版回执；本项目曾因此需要更正记录。

## 11 踩坑速查

| 现象或误区 | 原因或已知边界 | 处理与预防 |
| --- | --- | --- |
| 本地移动正常，线上全拒绝 | instanceof 把数据容器身份当协议合法性 | 有界规范化字节，增加宿主边界测试；已真机验证修复 |
| 敲蛋动画正常但不扣血 | 本次为权威位置停在出生点的连锁问题 | 对照操作回执和权威坐标，不先改伤害/距离 |
| 摇杆动但人物冻结 | 本次一阶段为 Room fuel 耗尽后失去 ready | 读关闭事件和可信告警，终止后给出重连路径 |
| 15 秒总超时一直相同 | 外层超时遮住 SDK 自身等待与重试 | 诊断时保留 SDK 预算和原始安全错误码 |
| ready=true 就以为联机成功 | 只证明初始基线收齐 | 增加持续收发、采纳、应用和回执证据 |
| 几个守卫也触发预算 | 大搜索空间、重复搜索及每邻居高成本 | 预烘焙、全局预算、增量求解、缓存上限 |
| 加缓存后本地快、恢复不一致 | 状态藏在对象外，或路线共享引用 | 权威状态入快照；逐 tick 恢复对比 |
| 部署了却仍看到旧行为 | 旧 Room 固定旧 Artifact，或客户端仍旧包 | 核对运行版本后重新进入，分别处理两条发布链 |
| 反复升 revision 期待修复 | 版本隔离不改变业务 bug | 只按兼容需要或明确版本隔离要求升版 |
| 同一账号开两个页当双人 | 身份重复，可能冲突或占用 | 两个独立身份，核对 roster 和 Room |
| 广告前卡住 | 本项目曾为旧 Mock 未加载新操作 | 检查实际进程和代码，再查广告 SDK |
| 手机还有已删除的按钮 | 原来只在细指针设备隐藏 | 检查 DOM、媒体条件和打包内容 |
| 多指操作互相打断 | 第二指统一切缩放并清移动 | 按起始区域固定手势归属 |
| 商店按钮偶尔点不动 | 账户刷新在按下/松开间替换 DOM | 稳定节点、原位更新，做实际输入回归 |
| 联机后路牌或反馈缺失 | 初始化分支提前返回，或把表现绑定低频同步 | 分离权威模拟和本地表现 |
| 账号问题就想清档 | 另一个账号正常不能证明存档损坏 | 先区分阶段、存储类型、错误码与版本 |
| 批量写成功就认定存档完整 | 多键写入不一定原子，可能部分失败 | 使用对应存储契约和提交点，测试响应丢失与恢复 |
| 支付按钮能用就认定完成 | 商品声明、发货归属、幂等及真实订单是不同环节 | 对齐 manifest 与运行表，按客户端或 Room 归属单端结算 |
| Windows 启动部署工具失败 | 曾遇到含空格路径转义错误 | 先定位启动器和参数引用，不绕过检查或授权 |
| 读到回执就宣布部署成功 | 可能是异步构建期间的旧回执 | 等最终退出成功，再核对当次身份和哈希 |
| 日志为空就判断没问题 | 未进 Room、未写日志、无记录或查询失败 | 按阶段找证据，并检查查询完整性 |
| Node 优化一半就宣称手机翻倍 | 算法耗时、fuel 和 GPU 帧率是不同量 | 各自测量，各自报告 |

## 13 下一次排障的工作顺序

1. **固定现场。** 确认设备、客户端 Bundle、兼容修订、Room 和 Artifact；不要先改协议、清档或大改打包。
2. **按链路定位。** 先判断连接、初始同步、输入、收包、解码、校验、广播、渲染、回执中的哪一步失败。
3. **首轮就采够信息。** 有界计数、具体拒绝分支、版本和时间一次设计完整，减少用户反复重进。
4. **先做失败回归。** 用实际发现的边界条件让旧代码失败，再验证修复；Mock 没覆盖的差异用针对性测试补齐。
5. **保持改动集中。** 不因遇到症状就放宽权威规则、换协议号、同时改资源与 UI。
6. **完成真实验证。** 部署成功后确认新 Artifact，结合用户看到的结果与服务端证据收尾。
7. **留下可继承记录。** 更新指南和测试，把待办与已验证分开；诊断工具保留开关，正式构建检查关闭。

本次改进责任在实现和验收：类型假设过窄、测试偏向同环境往返、最初拒绝原因记录不足。线上验证仍有必要，但这类边界 bug 应尽量前移到本地测试发现。



### 补充复盘：旁观人物忽近忽远

位置消息的到达时间不等于位置的采样时间。两个包相隔 1ms 到达，不代表人物在 1ms 内跑完对应距离；拿这个速度继续外推，会冲过头，随后被新数据拉回。本项目旧 MotionBuffer 使用到包时间并外推 150ms，普通匀速本地测试难以暴露此问题。修复透传现有 MOVES 的 Room 时间戳、处理 uint32 回绕、固定 180ms 缓冲并取消超出最后确认点的外推；丢包时允许停住。回归必须涵盖压缩到包、乱序、丢包、急停，以及直线前进时显示位置是否无故倒退，不能只验证外推距离有上限。真实权威位置发生纠正仍可改变移动方向，本修复不声称消除所有网络卡顿。

### 补充复盘：行走被拉回（2026-10-25）

正常移动包因到达间隔不足 80ms 被丢弃，本身不等于玩家移动违规。旧 Room 把所有 acceptMove=false 都交给位置纠正分支，差距超过 2 单位就给客户端发送旧位置；客户端立即 teleport，形成周期性回退。近期线上日志有大量 INTERVAL；实际 Room handler 的模拟到包测试可稳定复现错误纠正，不必等真机才能发现。

修复按当前包的明确拒绝原因区分：INTERVAL/SEQUENCE/格式错误不产生位置纠正，DISTANCE/VERTICAL/BOUNDS 才进入空间纠正条件。不能用累计日志中残留的上一包错误原因做本包决策，不能为了消除拉回直接移除速度预算。验收不仅检查服务器有没有接受位置，还要检查“合法移动被丢弃后有没有错误的纠正副作用”；用例应包含相邻到包、乱序、持续合法移动和真正的瞬移。低频统计同时记录接受数、纠正数及纠正原因，不能仅凭最后一次拒绝原因认定每次画面抖动的根因。

WebGL2 可创建不等于整帧可渲染。旧 Chromium 实测全局 MAX_SAMPLES 可大于 RGBA16F 支持采样数，直接套用会使 framebuffer 不完整；应取颜色/深度格式支持值交集。sRGB mip 生成也可能无错误却返回空内容，使透明裁切模型消失；本工程运行时读回一个微型测试纹理，仅检测失败才降级，不靠 UA 一刀切关闭画质。还必须检查实际截图中的地图和人物，不能只看 ready=true 或 JS 无异常。
